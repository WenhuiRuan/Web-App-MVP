# 工作流说明

阮文慧

我使用 Codex 分阶段完成这个项目，应用运行时接入 DeepSeek。先确定用户流程和数据关系，再做页面、讨论引擎及模型接入。每一阶段都有对应的任务指令、验证记录和 Git 提交，发现问题后再针对受影响的部分修改。

## 开发过程

需求分析时，我把创建议题、生成嘉宾、确认阵容、观看讨论和查看总结串成一条流程，再逐项对应题目的验收要求。SDD 阶段定义讨论状态、角色与消息归属、SQLite 数据模型以及 HTTP/SSE 接口，随后初始化前后端工程。DDD 阶段按前端设计驱动推进，用模拟客户端完成首页、阵容页和演播厅，调整普通屏、超宽屏和窄屏下的布局与独立滚动。

核心业务按 TDD 推进，先写生命周期、重复启动、消息引用和事务失败等用例，再实现业务。E2E 使用实际 React、FastAPI、SQLite 和 SSE，模型由可控替身提供，检查创建到总结的完整流程、断线补发及多讨论隔离。接通真实模型后，我根据实际发言核对职业视角、回应关系、观点来源和总结内容，分别记录工程验证与内容复核结果。

## 遇到的问题

最初的专家发言接近固定轮转，主持人也缺少追问。排查后发现，近期出场惩罚压过了直接回应的价值，主持追问又可能被专家候选跳过。我先让 Codex 复现这两种情况，再修改仲裁和主持发言路径。后续真实讨论中出现了质疑、原作者回应和收窄条件的连续交锋，说明调度修改确实影响了讨论过程。

观点提取存在重复共识、条件扩大和分歧一直为空的问题。我分别核对共识的共同支持，以及分歧双方各自的相反判断。一次就业议题在第9、10条出现相反判断，第11条作出澄清，但第10条的过程提取被结束流程取消。修复后，正常结束会保留有效的过程提取，再检查最终完整消息范围；可控浏览器用例覆盖了分歧出现和后续化解。

真实模型输出不合格时，早期实现会中断讨论，只留下笼统错误码。我补充了安全诊断和具体纠正反馈，并将重试集中在统一调用层。非开场主持发言连续不合格时，可以在有限次数内跳过；认证、取消和数据库错误仍按原规则处理。早期失败没有保存原响应，无法还原的原因继续保留为未确定。

## 我的体会

开发中，我逐渐把确定的规则交给契约、事务和状态检查，把讨论内容交给有来源的复核。这样既能限制非法结果入库，也方便定位模型表现与工程实现各自的问题。交付版本为 ae2f54a，已有真实完整讨论记录；最新诊断、开场和分歧修复通过了可控验证，尚未重新做整场真实模型验证。模型语义判断和等待时间仍有改进空间。
